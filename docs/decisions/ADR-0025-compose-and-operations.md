# ADR-0025: Compose and operations

- Status: Accepted
- Date: 2026-09-28 (M7; recording form)

## Context

The brief wants `compose.yaml` with the services `api` and `web`, a `SKY_DATA_DIR` bind mount for `DATA_DIR`, healthchecks and `.env` (l.489), `make up` / `make down` (l.346), nginx on 80/443 (l.20), both TLS paths documented (l.96), a weekly `sky-data update` cron line with the `docker compose restart api` reminder (l.298), the closed `SKYAPI_` variable list (l.397), `/health` `starting` driving the Docker healthcheck (l.80) and the definition of done from a clean clone (l.490-491). M6 handed over `FORWARDED_ALLOW_IPS=<compose network>` (never `*`) for the rate-limit key, a container memory limit for a worker serving concurrent 100-body frames (R114: 0.90-1.01 GB anonymous RSS per worker in flight), `SKY_DATA_DIR=./data` uncommented in `.env.example` and compose setting `SKYAPI_DATA_DIR=/data`. Compose facts verified on 2026-09-27: `env_file: - path: .env  required: false` (>= 2.24), `depends_on: condition: service_healthy`, `healthcheck.start_interval` (>= 2.20.2), `deploy.resources.limits.memory` honoured by `docker compose up`, `!override` (>= 2.24): every key used exists on Compose 2.38.2 (the runner), 5.1.3 and 5.3.1 (here); `security_opt: [no-new-privileges=true]` in the `=` form (the `:` form warns); Docker never restarts an unhealthy container (moby `health.go` sets the status and emits an event; `restart:` policies act on exit only); `up --wait` exits 1 with "dependency failed to start: container ... is unhealthy" and the dependent service is not started; a bind mount whose source is missing is created root-owned unless `create_host_path: false`; the nginx image's read-only run needs writable `/etc/nginx/conf.d`, `/var/cache/nginx` and `/run`, and its root master needs `KILL` to signal the uid-101 workers once `cap_drop: [ALL]` applies; uvicorn's `FORWARDED_ALLOW_IPS` accepts networks in CIDR form and takes the first untrusted address from the right; `.env` values reach the api container through `env_file`, so a `COMPOSE_FILE` line there would leak into it. The host `data/` (uid 1000) holds 3,949,027,410 B here.

## Options considered

1. The proxy trust: `FORWARDED_ALLOW_IPS=*` (rejected: any client forges `X-Forwarded-For`), the `web` container's address (rejected: it changes on every re-creation), the compose network in CIDR form written once (chosen: `x-sky.subnet: &sky_subnet 10.213.0.0/24`, outside Docker's default pools and WSL 2's NAT range, used by `FORWARDED_ALLOW_IPS` and by `networks.default.ipam.config`; the docker host itself, the gateway `10.213.0.1`, is trusted: accepted; maintainer question 44).
2. Overlays versus one file: everything in `compose.yaml` with profiles (rejected: TLS ports and an e2e image in the production file), `compose.tls.yaml` and `compose.e2e.yaml` beside it (chosen, backlog B-102; the e2e overlay must be impossible to confuse with a deployment), `compose.override.yaml` gitignored for local ports and subnet.
3. The data directory of a clean clone: Docker creating `./data` (rejected: root-owned, `sky-data` then fails with `PermissionError`), a documented `mkdir` (rejected: the two-command definition of done), `data/.gitkeep` tracked with `.gitignore` `/data/*` + `!/data/.gitkeep` and `create_host_path: false` (chosen, backlog B-103: a clone owns `data/` as the cloning user, uid 1000 here = the image default; `SKY_UID`/`SKY_GID` for other hosts; a `PermissionError` stays a traceback at M7, plan Q88).
4. Documentation homes: a new `docs/deployment.md` (rejected: l.431's closed list, D165), the runbook and checklist in `docs/architecture.md` "Deployment", the probe outcomes in `docs/testing.md` "Delivery (M7)", the acceptance record and the final report closing `docs/plan.md` section 6 (chosen).
5. Failure semantics: an autoheal sidecar or `restart: always` on health (rejected: Docker has no such policy and a sidecar is out of scope), the truth documented (chosen, D200).
6. Acceptance: the developer tree (rejected: l.490 says a clean clone), a real `git clone` of commit 1 with its own project name, two runs (de440s from the unmodified `.env.example` on the clone's own empty `./data`; the existing de441 directory), the e2e suite through nginx via the e2e overlay, the native gates in the clone (chosen, D196).

## Decision

Records plan rows D187, D188, D189, D194, D195, D196, D199 and D200 (with backlog B-101, B-102, B-103, B-108 and risks R116, R119, R120, R139-R143, R146-R150).

### D187 `compose.yaml`

`name: intersidera`; `api` (build `./backend`, `image: intersidera-api:local`, `env_file: [{ path: .env, required: false }]`, `environment: { SKYAPI_DATA_DIR: /data, FORWARDED_ALLOW_IPS: *sky_subnet }`, the D171 `command`, the bind `${SKY_DATA_DIR:-./data}:/data` with `create_host_path: false`, `user: "${SKY_UID:-1000}:${SKY_GID:-1000}"`, `read_only: true`, `tmpfs: [/tmp:size=64m,mode=1777]`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges=true]`, the D172 healthcheck, `restart: unless-stopped`, `deploy.resources.limits.memory: ${SKY_API_MEMORY_LIMIT:-2G}` and `memswap_limit: ${SKY_API_MEMORY_LIMIT:-2G}` (Q97 revisited on 2026-09-28 after the rehearsal: equal limits give the api no swap, Docker would otherwise grant as much swap again, and the e2e rehearsal showed what host swap thrash does; an anonymous overrun is an OOM kill and `restart: unless-stopped`; 1 GB plus 1 GB per worker; measured on this machine about 30 s after a warm start on de440s, 2026-09-28: `memory.peak` 1,557,237,760 B of which `anon` 771,280,896 B, the rest the reclaimable page cache of the mapped kernels and caches, against `memory.max` 2,147,483,648 B; the first-start peak with a cache build is the acceptance run's figure in `docs/testing.md` "Delivery (M7)"), json-file logging `10m` x `3`); `web` (build `./frontend`, `image: intersidera-web:local`, `depends_on: { api: { condition: service_healthy } }`, `SKY_GEOCODER_ORIGIN` and `SKY_WEB_MODE` with defaults, `ports: ["80:80"]`, `read_only: true`, `tmpfs: [/etc/nginx/conf.d:size=1m, /var/cache/nginx:size=256m, /run:size=1m]`, `cap_drop: [ALL]`, `cap_add: [CHOWN, SETGID, SETUID, NET_BIND_SERVICE, KILL]`, the same `security_opt`, the D175 healthcheck, `restart`, logging); `networks.default.ipam.config: [{ subnet: *sky_subnet }]`; no `version:`, no named volume. Backlog B-108 records the keys beyond l.489's list.

### D188 Proxy trust

Option 1: the subnet written once; uvicorn trusts `X-Forwarded-For` from that network only, so remote clients cannot forge the rate-limit key; a collision ("Pool overlaps") changes both uses through `compose.override.yaml` (R140); an external TLS proxy off the compose network is appended there (ADR-0003 amendment).

### D189 Overlays

`compose.tls.yaml` (`SKY_WEB_MODE: tls`, `ports: ["443:443"]`, `${SKY_TLS_DIR:-./certs}:/etc/nginx/certs:ro` with `create_host_path: false`; rotation = copy + `docker compose exec web nginx -s reload`); `compose.e2e.yaml` (acceptance only: `api` `SKYAPI_EPHEMERIS=de440s.bsp`, `SKYAPI_AUTO_FETCH="false"`, `ports: ["127.0.0.1:8000:8000"]`; `web` `build.args.BUILD_SCRIPT: build:e2e`, `image: intersidera-web:e2e`, `ports: !override ["127.0.0.1:4173:80"]`); `compose.override.yaml` gitignored; `COMPOSE_FILE` documented as a shell export, never a `.env` line (Q96).

### D194 Data directory policy

Option 3; the compose-tier variables `SKY_DATA_DIR` (uncommented), `SKY_UID`, `SKY_GID`, `SKY_API_MEMORY_LIMIT`, `SKY_WEB_MODE`, `SKY_TLS_DIR` in `.env.example` beside the documented `WEB_CONCURRENCY` (backlog B-101; the closed `SKYAPI_` list of l.397 stays).

### D195 Documentation homes

Option 4; `docs.md` gains the final-report clause; no new docs file; no prettier gate on YAML or Markdown at M7 (Q98).

### D196 Acceptance protocol

Option 6: `git clone` of commit 1 into `~/tmp/intersidera-m7-<date>/clone` with `COMPOSE_PROJECT_NAME=intersidera-acc`; run 1 = `cp .env.example .env` unmodified (de440s, `SKY_DATA_DIR=./data`: the clone's own empty `data/`, which `data/.gitkeep` provides, so the two commands of brief l.490 run as a clean clone runs them), `config -q` x4 (once without `.env`), build, fetch, `up --wait`, the first-start and warm ready times, `memory.peak`, the probe table, the e2e suite and Lighthouse through nginx via `compose.e2e.yaml` (chromium-desktop and chromium-mobile, `--workers=2`), `make setup/check/test/e2e/build` natively in the clone, `make images`; run 2 = the existing 3.95 GB directory on de441; the literal `.env`-less definition of done (a 3.3 GB download) documented, not executed; two commits (`build: docker compose, images and release checklist`, then `docs(plan): M7 acceptance record and final report`), `make check` green, never pushed. Outcomes: recorded in `docs/testing.md` "Delivery (M7)" and in the acceptance record of `docs/plan.md` section 6 (the second commit).

### D199 Operations

Weekly cron in compose form `15 4 * * 1  cd /srv/intersidera && docker compose run --rm api sky-data update && docker compose restart api` beside the host form (l.298); `web` needs no restart (the `resolve` upstream picks up the re-created `api` within 10 s); `sky-data fetch` downloads the configured ephemeris (`--full` adds de441 when the configuration is de440s; without `.env` the fetch downloads de441); `docker compose run --rm api sky-data build-caches` as the optional pre-build; certificate rotation by copy + `nginx -s reload`; the `.bootstrap.lock` serialises the API's workers only (a `sky-data` run is not serialised against a running API, hence update then restart).

### D200 Failure semantics documented truthfully

A fatal bootstrap keeps the process up, `/health` answers 503 with `detail`, the container turns `unhealthy` after the start period plus three probes (about 390 s) and is never restarted by Docker or Compose (`restart: unless-stopped` acts on exit only); `up --wait` exits 1 with "dependency failed to start: container ... is unhealthy" and `web` is not started; recovery = `docker compose logs api`, fix the data, `docker compose restart api`; `docs/data.md` quotes the remedy with `DATA_DIR`, not `/data` (ADR-0008 amendment).

## Consequences

- `docker compose up` from a clean clone needs `.env` (or accepts the code defaults: de441 and a 3.3 GB auto-fetch inside the container, which exceeds the 300 s start period, R120: `unhealthy` after about 390 s, `web` not started, the download continues, a second `up -d` recovers; the documented order is fetch first).
- The hardening (`read_only`, `cap_drop`, `security_opt`, the sized tmpfs mounts) is staged: first without, `make up` green, then with, re-proved (probe 27 proves the `KILL` capability: `docker compose stop web` under 2 s and `nginx -s reload` without a `failed` log line; R143).
- The developer tree and the clone share `name: intersidera` unless `COMPOSE_PROJECT_NAME` differs (R147); a Windows-side listener on 80/443 is invisible to `ss` (R146: `netstat.exe -ano`); every stack figure is a Docker Desktop on WSL 2 figure (R150); one rate-limit bucket keys every Playwright worker behind nginx (R149: a 429 in the run is not a regression); Playwright launches its own servers when 8000 or 4173 do not answer 2xx (R141: the protocol curls both first).
- Recorded deviations: B-101 (the compose-tier variables), B-102 (the overlays), B-103 (`data/.gitkeep`), B-108 (the compose keys beyond l.489).

## Revisit trigger

- Compose gains a health-based restart policy or Docker restarts unhealthy containers (D200 and the runbook change); the maintainer answers questions 44-51 (the subnet, the uid policy, the memory rule, `SKYAPI_AUTO_FETCH` in production, deriving `SKYAPI_GEOCODER_URL` from `SKY_GEOCODER_ORIGIN`, the production values, log rotation, the build labels); the first-start `memory.peak` exceeds 1.8 GB (the 2G default moves); `sky-data` learns to report a `PermissionError` (Q88); the acceptance protocol runs on a host other than Docker Desktop on WSL 2.

## Amendment (M7, 2026-09-28)

The M7 fix pass after the adversarial review (plan D187 and D188 amended on 2026-09-28; the stack re-measured on 2026-09-30, the figures quoted in each item); the decision text above is unchanged.

- D188, the proxy trust (review finding 1, MAJOR). The trusted set is no longer the compose network but `web`'s fixed address on it: `x-sky: { subnet: &sky_subnet 10.213.0.0/24, web_address: &sky_web 10.213.0.3 }`, `web.networks.default.ipv4_address: *sky_web`, `FORWARDED_ALLOW_IPS: *sky_web` (never the /24, never `*`). Option 1 rejected the `web` address because "it changes on every re-creation"; a fixed `ipv4_address` removes that objection. The sentence "the docker host itself, the gateway `10.213.0.1`, is trusted: accepted" is superseded: the gateway relays every host connection and, behind Docker Desktop's userland proxy (and, per Docker's port-publishing documentation, for the IPv6 clients of a port published without a host address on the IPv4-only network), every published-port connection, so with the /24 trusted uvicorn walked past the gateway into the client-supplied part of `X-Forwarded-For`: the rehearsal's probe 16 saw a forged header answer 200 three times out of three while unforged requests in the same process answered 429. With the address alone uvicorn stops at the first untrusted address from the right, the one nginx itself appended (`$proxy_add_x_forwarded_for`: the real client on a Linux host, the gateway behind Docker Desktop), so a client-supplied entry is never reached and a forged header is keyed like an unforged one; the host stays one bucket behind Docker Desktop (R149 unchanged). An external TLS proxy whose `X-Forwarded-For` must be honoured is appended after the web address in `compose.override.yaml`, its address as nginx sees it (D182); in `compose.e2e.yaml` the published 8000 lets host clients reach uvicorn directly from the untrusted gateway, so their header is ignored (loopback only, acceptance only). A collision ("Pool overlaps", R140) now changes every use in the override: the subnet, the address and the variable. nginx and `scripts/check_nginx_headers.mjs` are unchanged. Re-measured on 2026-09-30 on the stack of the milestone tree (probes 16 and 21 of `docs/testing.md` "Delivery (M7)"): `web` at `10.213.0.3`, the api at `10.213.0.2`, `FORWARDED_ALLOW_IPS` `10.213.0.3`; after a same-process keep-alive burst emptied the host bucket (1,500 frame requests in 2.04 s: 80 x 200 / 1,420 x 429), six requests interleaved forged (`X-Forwarded-For: 203.0.113.7`) and unforged answered 429 six times out of six, in each of three tails; over 30 such tails per header variant (`203.0.113.7`, the trusted `10.213.0.3` itself, `203.0.113.7, 10.213.0.3`, `10.213.0.9`) the forged requests answered 200 once or twice in 90, like their unforged neighbours (one to three in 90: the refill of one token per 50 ms); the control with the /24 restored through a scratch override file reproduced the weakness with the same script (forged 200 three times out of three in each of three tails, unforged 429) and the committed file closed it again; 20 of 20 requests from inside `web` (source `127.0.0.1`, untrusted, keyed apart) answered 200 during a second host storm (8.00 s: 199 x 200 / 6,579 x 429).
- D187, the web tmpfs mounts (review finding 2). `tmpfs: [/etc/nginx/conf.d:size=1m,mode=0755, /var/cache/nginx:size=256m,mode=0755, /run:size=1m,mode=0755]`: Docker's default tmpfs mode is `1777`, which let the uid-101 workers write the directory holding the rendered `00-headers.conf` and `10-site.conf` that the root master re-reads on `nginx -s reload` (the certificate-rotation step); the entrypoint renders as root and the master writes `nginx.pid` and creates the `*_temp` directories itself, so nothing needs a world-writable mount. Re-measured on 2026-09-30 (probes 24 and 27): `HostConfig.Tmpfs` `{"/etc/nginx/conf.d":"size=1m,mode=0755","/run":"size=1m,mode=0755","/var/cache/nginx":"size=256m,mode=0755"}`, the three mounts `mode=755` in `/proc/mounts`, the rendered files root-owned at 0644, the five `*_temp` directories created by the master and owned by `nginx` at 0700; `docker compose stop web` 0.656 s with exit code 0, `nginx -s reload` exit 0 with the ten workers replaced and no `failed` line; the api `Memory` = `MemorySwap` = 2147483648 and `memory.swap.max` 0 in its cgroup. `memswap_limit` (Q97) was already recorded in D187 above.
- D187, what `KILL` is for (measured on 2026-09-30; the Consequences above and R143 say that probe 27 "proves the `KILL` capability", which the control does not confirm). The web image started with the compose flags but without `KILL` stops as fast (0.475 s against 0.506 s with it, exit code 0) and reloads as cleanly (the workers replaced, no `failed` line): nginx's master commands its workers through their channels for a reload and for a graceful or a fast shutdown, and calls `kill()` only as the fallback and for the `SIGKILL` of a worker that ignores a fast shutdown. With one worker stopped by `SIGSTOP` and a `SIGTERM` sent to the master, the container without `KILL` logged `kill(29, 9) failed (1: Operation not permitted)` and was still running 12 s later, while the container with `KILL` logged `worker process 29 exited on signal 9` and exited 0 within 3.5 s. `KILL` stays in `cap_add` for that escalation; probe 27 proves the stop and the reload under the hardened set, not the need for the capability.
